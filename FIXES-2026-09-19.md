## 1. What was fixed

### Deployment (this is why your app never worked offline)

**`service-worker.js`** — every one of the 38 precache paths was root-absolute (`'/index.html'`). Your app is served from a `/Hans-Scedule/` subfolder on GitHub Pages, so all 38 requests hit the wrong address and the install failed silently. Now relative.

Also in the same file:
- Cached HTTP 206 partial responses (from `<audio>` range requests), which could corrupt your chime sounds. Now skipped.
- Added an offline navigation fallback, so a failed page load serves `index.html` instead of the browser error screen.
- `skipWaiting()` was called outside `waitUntil()`; now inside, as the spec expects.
- Cache version bumped `v31` → `v32`, so the old broken cache gets purged on next load.

**`manifest.json`** — `start_url`, `scope` and `id` were all `/`, pointing outside the app's own folder. Now relative.

### Security

**`js/shared.js`** — `escapeHtml()` rewritten. It previously escaped `& < >` but **not quotes**, which made every attribute context injectable. It now escapes `& < > " '` explicitly. This single change closes roughly a dozen injection points at once, because most of the codebase already called `escapeHtml` — it just wasn't protecting against quotes.

Added **`safeColor()`** — a validator that only accepts real colour values (hex, named, rgb/rgba, CSS var). Anything else falls back to a default.

**`js/friends.js`** — four places where another user's `avatarColor` was inserted straight into a `style="background:..."` attribute with no validation. This was the cross-user attack path: a hostile user sets a crafted colour on their own profile, and it runs in every friend's browser. Now passed through `safeColor()`.

**Tag-name injection** — `TAG_LABELS[tag]` was being inserted unescaped in 9 places, several of them inside attributes:
- `js/progress.js` — 7 sites (board column header, add-task tooltip, pie chart tooltip, bar chart tooltip, legend rows, two toast messages)
- `js/schedule.js` — 1 site (pomodoro chip)
- `js/hub-visuals.js` — 2 sites (Spotify playlist name, gallery colour field)
- `js/goals.js` — 1 site (goal icon)

### Memory leaks and runaway loops

**`js/hub-visuals.js`** — three fixes:
1. The flight-radar cleanup ran **870 lines after** the grid had already been emptied, so it never found anything to clean. Every hub re-render leaked a Leaflet map, its event handlers, and a `setInterval` hitting the network every 15 seconds. Moved above the wipe.
2. The timer tick started whenever any timer state existed — even with nothing running — and rewrote localStorage **5 times per second, forever**, on every page load. Now only starts when a timer is actually running.
3. The clock's 1-second interval was never cleared. Now stops when the last clock widget is removed.

**`index.html`** — `HUB_MOBILE_DISABLED` only added a CSS class to hide the canvas. All the renderers and fetchers still ran below 768px — invisible, draining battery and data. Now the hub doesn't initialise at all on those devices.

### Data safety

**`js/shared.js` — the backup was incomplete.** This is worth understanding, because the audit I gave you earlier pointed at the wrong function.

Your app has two export buttons. One (`exportAllData` in `settings.js`) exports *settings*. The other (`exportData` in `shared.js`) is the real data backup — and it only saved **tasks and sleep**. Goals, finance, piggybank, wallet, activity history and gallery layout were all missing.

If you had restored from a backup, you would have silently lost all of it.

Now exports all of them, and the restore only writes keys that are actually present in the file — so an old backup can never wipe newer data.

## 2. NOT fixed — these are genuinely dangerous

I stopped short on these on purpose. Each one can lose data or break the app if done carelessly.

### 2a. The `28:45` clock bug — needs a careful, narrow fix

`toTimeStr()` has no wrap-around, so 4:45am next day is written as `"28:45"`.

**Why I didn't just add `% 1440`:** three places in `js/shared.js` (lines ~3793, ~6719, ~6759) use `toTimeStr(START_HOUR * 60 + VISIBLE_HOURS * 60)` to describe your grid to the AI as `"05:00 – 29:00"`. Adding the modulo would silently change those prompts to `"05:00 – 05:00"` and confuse the assistant.

The correct fix is to wrap only at the five call sites that **write to task records** (`js/schedule.js` ~2030, 2031, 2043, 2044, 2052, 2053, 2084, 2085, 2204). That's a surgical change I'd rather make with your go-ahead, and it still leaves any already-saved `"28:45"` values in place — those need a separate one-time cleanup.

**Your call:** want me to do the narrow version?

### 2b. Storage-full errors are swallowed

The `localStorage.setItem` wrapper catches "storage is full" and returns quietly. Your own quota handling has therefore never run once — the code that should warn you is unreachable.

**Why I stopped:** the fix is to make it *throw* or return a failure flag — but every caller would then need updating, and any caller that doesn't expect a thrown error would break. This is a genuine refactor, not a one-line change.

### 2c. Startup can be killed by one bad value

`loadState()` loads ten things — settings, API key, tags, categories, card colours, profile, images — inside a **single** `try` block. If item #2 is corrupt, everything from #3 onward silently never loads.

**Why I stopped:** this is the boot sequence. Get it wrong and the app doesn't start at all. It needs the try blocks split one at a time, with testing between each.

### 2d. Deleted images are never actually deleted

Removing an image bubble only removes the tile. The image itself stays in storage forever.

**Why I stopped:** the fix is to delete the image when its last tile is removed — which requires checking whether any other tile still uses it. Get that check wrong and you permanently delete images you wanted to keep.

### 2e. Your AI key is synced to the cloud

`js/firestore-sync.js` pushes every `haven-*` key to your Firestore document, including `haven-schedule-apikey` (your Groq/Gemini key) and the admin password hash.

**Why I stopped:** excluding them changes what the cloud copy contains. Existing cloud documents still hold the old values, so the fix needs a decision about cleaning those up too — and that touches other people's data if anyone else has an account.

### 2f. Money is stored as decimals

Finance amounts are summed as floating-point numbers. With enough entries the totals can drift by a cent or two.

**Why I stopped:** the proper fix is storing integer rupiah, which means converting every existing record. That's a data migration, and a bad migration corrupts your finance history.

### 2g. Changes that alter what you see

Technically safe, but they change displayed numbers or behaviour, so you should decide:

- **Streak counts are wrong** — computed from week-filtered data, so any streak crossing a week boundary breaks. Fixing it makes your streak numbers go *up*.
- **The Day-by-Day table** only counts unfinished tasks, so completing work makes the totals go *down*. Fixing it changes those columns.
- **The period filter has no upper bound**, so future-dated tasks are included in this week's totals. Fixing it makes some tasks disappear from the view.
- **Work-hours mode draws everything 2 hours too low** — a visible layout change.
- **`copyWeekToNext` shifts dates by one day** in negative-UTC timezones.
- **Dragging a repeating task** silently does nothing while moving your *other* tasks instead.
- **The hub is disabled on mobile** — I stopped it wasting resources, but whether to *re-enable* the bento canvas on phones is a product decision, and it's your most distinctive feature.
