## Rhythm page reworked

Hans asked to "make the rhythm page better, nicer, and not showing the app already
in the back". Clarified before building — his answers:

- **"the app in the back"** = the app shell (sidebar + footer) visible around the wizard.
  He explicitly did **not** want anything deleted. Resolution: hide the shell with CSS
  on this page only; the sidebar markup stays in `rhythm.html` untouched and every
  other page is unchanged.
- **Look:** app-native (match the app's own tokens, not a separate design language).
- **Length:** trim 7 steps → 5.
- **Placement:** first-run onboarding.

### What changed

`rhythm.html` (334 → 435 lines) and `js/rhythm.js` (543 → 607 lines).

1. **First-run detection** — an inline script in `<head>` (before the stylesheet, so the
   shell never flashes) scans `localStorage` for any key containing `haven-rhythm-answers`.
   Prefix-agnostic on purpose: the per-account `_p()` monkey-patch means the real key is
   account-prefixed, so a plain `getItem('haven-rhythm-answers')` would always miss.
   No answers → `html.rhythm-firstrun` → sidebar, overlay and minifooter hidden.
2. **Returning users keep the shell** — otherwise clicking Rhythm from the sidebar would
   be a dead end with no way back. Their saved answers make the class not apply, and the
   wizard opens on Review as before.
3. **7 steps → 5:** You / Priorities / Your day / Planning / Review. Wake+sleep+commitments
   merged into one screen; the goal line moved onto the Planning screen; the
   keep-subjects toggle moved onto Review (it decides what gets created).
4. **New stepper** — five labelled segments with an `aria-current="step"` marker, replacing
   seven anonymous dots.
5. **Polish** — sticky hero so the step indicator stays visible, per-step entrance
   animation (respects `prefers-reduced-motion`), live "Awake roughly 06:00 – 23:00 · 17h"
   readout, `aria-pressed` on options, focus rings, responsive down to 640px.

### Bugs found and fixed along the way

- **`.rhythm-btn-primary` was white-on-white in dark mode.** It set `color: #fff` on
  `background: var(--accent)`, but `--accent` resolves to `--user-primary` which is
  **#ffffff in dark mode**. The "Next" / "Apply preset" label was invisible. Fixed to
  `color: var(--on-primary)`. Worth checking other pages for the same pattern.
- **"Nothing fixed — my time is flexible" could be combined with real commitments.**
  Now selecting it clears the others, and selecting a real one clears it.

### Verification method that worked well

`agent-browser` is **not installed** and needs ~500MB of Chromium. Chrome and Edge are
already on this machine, so instead:

1. Build a throwaway harness (`__rhythm-preview.html`) = `rhythm.html` with the auth/sync
   scripts stripped (`gsi.js`, `supabase*.js`, `premium*.js`, `settings.js`). `rhythm.html`
   redirects to `login.html` without a session, so it can't be previewed directly.
2. Serve with `python -m http.server 8777 --bind 127.0.0.1`.
3. `chrome --headless=new --no-proxy-server --hide-scrollbars --window-size=1400,980
   --virtual-time-budget=5000 --screenshot=out.png "url?s=scenario"`.
   `--no-proxy-server` is required here — a system proxy returns 502 for localhost.
4. Scenario switching via `?s=` and a trailing script. `_rhythmStep` is a top-level `let`,
   so it is reachable by name from a later inline script but **not** via `window`.
5. Delete the harness afterwards. (Root already has `__dom-dump.html` and
   `__spotify-test.html` left over from earlier sessions — those should go too.)

**Trap to remember:** forcing light mode with `classList.add('light')` after load gives a
false result. `applyAccentColor()` reads `isLight` when it runs, so the class must be set
via `state.darkMode = false; applyTheme();` or `--user-primary` keeps the dark value and
you get a phantom white-on-white button. I hit this and nearly "fixed" a non-bug.

## Follow-up: Rhythm is now first-run only (same day)

Hans changed his mind on the earlier "don't remove anything": Rhythm should now appear
**only when an account is created**, and should be **out of the sidebar everywhere**.

### Routing

Every account-creation path used to end at `index.html`. Two functions in `js/gsi.js`
decide where auth lands:

- `completeGoogleSignIn(gdata)` — its `finish(targetId, isNewAccount)` helper now sends a
  **new** account to `rhythm.html` and an existing one to `index.html`. This is the path
  that matters: the Supabase sign-up *and* sign-in forms both call `googleSignIn()`, so the
  discriminator is the `localUsers.find(u => u.googleId === ...)` lookup that was already
  there — not the form the user filled in.
- `createLocalProfile(name, opts)` — added an `opts.onboard` flag. Only the login page's
  sign-up fallback and the "Continue as Guest" button pass `{ onboard: true }`. Adding a
  profile from Settings or the account popup deliberately does **not**, or it would send
  people through onboarding for a secondary profile.

`login.html` line 1544 (sign-in) intentionally left alone → `index.html`.

### Other changes

- Removed the `<a href="rhythm.html" class="hub-snav-item">` line from **9 files**
  (index, schedule, progress, goals, finance, gallery, friends, premium, rhythm).
  Every page now has 7 nav items.
- `?redo=1` on `rhythm.html` skips the `rhythm-firstrun` class, so the app shell stays and
  the user can navigate back out. Added a **"Rhythm setup → Redo"** row in the Settings
  panel (`setRedoRhythm`) linking to `rhythm.html?redo=1`. This is the only way back in.
- `confirmRhythmApply()` now sends a first-run user to `index.html` instead of reloading —
  a reload would re-render the wizard with the shell suddenly around it.

### Verified

- Both `rhythm.html` modes screenshotted: plain = no shell + "Skip for now"; `?redo=1` =
  shell visible, sidebar shows 7 items, no "Skip for now".
- `node --check` on `gsi.js` and `rhythm.js`; both inline `<script>` blocks in `login.html`
  extracted and syntax-checked (24,857 chars — parses clean).
- No `href="rhythm.html"` left in any sidebar.

## Account switching: Hans reports "logged in with 2 accounts, profiles don't both appear"

Investigated `js/gsi.js`. Hans could not say which flow he used ("not sure / mixed").
Three defects found, one severe. **No code changed yet** — awaiting his go-ahead.

### A. "Sign Out" in Settings DELETES the account and all its data (severe)

`gsi.js:1437` — `setSignOut` handler calls `removeProfile(activeId)`, which pops
`confirm('Remove "<name>" and all their data?')` then runs `performRemoveProfile()`:
wipes every localStorage key prefixed `<id>:`, deletes IndexedDB `haven-images-<id>`,
drops the profile from `haven-gsi-accounts`. There is no plain sign-out anywhere.
Almost certainly what Hans hit: Sign Out → OK → profile 1 gone → sign in as 2 →
only one profile left. Data is unrecoverable unless the profile was Google/email-backed
and had synced to Supabase.

### B. Second Google sign-in while already signed in is silently ignored

`handleSupabaseAuthUser()` (`gsi.js:473-487`) starts with `if (getActiveUserId()) return;`.
OAuth from the avatar popup completes, redirects back, nothing happens — no profile, no
error. Worse: the Supabase session is now account B's while local profile A is still
active, so A's data syncs into B's cloud space.

### C. login.html bounces to index.html when already signed in

`initGSI()` `gsi.js:954-957`. So the email/password route for a second account is
unreachable without signing out or going through Guest.

### Also true, not a bug

Profile list (`haven-gsi-accounts`) is **device-local**, never synced — so accounts
created on two devices will never both appear on one. `haven-gsi-*` keys bypass the
per-account prefix (`shared.js:1893-1897`). Both list renderers (popup `gsi.js:271`,
settings `gsi.js:1259`) do render every entry — so a missing profile means it was
never created or was deleted, not a display filter.

### Fix applied (Hans approved "fix all three"; he also confirmed the deleted
### account's data came back — it was cloud-backed)

All in `js/gsi.js`. `node --check` passes. **Not rendered in a browser** — no session
here, and `index.html` redirects to `landing.html` without one.

1. **Sign Out is now a real sign-out.** `setSignOut` → new `signOutKeepProfile()`:
   clears `AUTH_ACTIVE_KEY`, clears `haven-guest`, `supabaseSignOut()`, then
   `login.html` (promise-driven, 1500 ms fallback). Profile and all `<id>:` keys stay.
   Added a separate `setDeleteAccount` button — "Delete this account and its data" —
   which keeps the old `removeProfile(activeId)` behaviour under an honest label.
   Sign Out no longer wears `set-btn-danger`; delete does.
2. **Second Google sign-in works.** SessionStorage markers `haven-gsi-oauth` (set by
   `gsiSignIn()`, consumed once by `handleSupabaseAuthUser`) and `haven-gsi-add`.
   `handleSupabaseAuthUser` now: `if (!_consumedOAuthIntent() && getActiveUserId()) return;`
   — so a passive session on load is still ignored, but a user-initiated OAuth is honoured
   and adds the account as another profile.
3. **login.html no longer bounces when adding.** `initGSI()`:
   `if (activeId && !_hasAddIntent()) { location.href = 'index.html'; return; }`.
   Marked by new popup buttons "Add account with email" (`accPopEmail`) and
   "Sign in with email instead" (`accPopEmailFull`), plus the existing guest button.
   Cleared in `completeGoogleSignIn()` and `createLocalProfile()`.
4. **`window.gsiSignOut = removeProfile` → `signOutKeepProfile`** (was gsi.js:2190).
   Nothing in-repo called it, but the exported name said "sign out" and did a delete.
5. Cosmetic: `setRemoveLocal` had a plus icon on a destructive button — now a minus.

### Still open

  — easy to miss when grepping for `initGSI(`.
- Working tree already had heavy uncommitted churn (Firebase config deleted from gsi.js,

## Follow-up 2: "new account" must mean no data, not no local record

Hans confirmed the intent: Rhythm appears **only** for a newly made account and from
Settings. He also noted that removing all accounts sends you to `login.html` — I verified
that is already true (`performRemoveProfile` and `guestSignOut` both do it when nothing is
left), so no change there.

The gap he was pointing at: my first cut decided "new account" from the **browser-local**
account list. Clearing site data, or using a new device, empties that list — so signing in
to a real account would replay the setup, and that is exactly what happens right after
removing all accounts.

### Fix: put the flag on the account, not the browser

- `markRhythmDone()` in `js/gsi.js` writes `{ data: { rhythm_done: true } }` through
  `supabase.auth.updateUser`. Called from `confirmRhythmApply()` and from the Skip handler.
- Read back as `user_metadata.rhythm_done` at all three entry points into
  `completeGoogleSignIn`: `handleSupabaseAuthUser` (OAuth return), `googleSignIn(gdata)`, and
  both `googleSignIn` calls in `login.html` (sign-in and sign-up).
- `var needsSetup = !gdata.rhythmDone;` — that one line is the entire decision.
- Guests have no cloud account, so `updateUser` fails harmlessly and they keep relying on the
  local answers key. Skip also counts as "seen", so it does not come back on another device.
- The Skip link needed `e.preventDefault()` + a 500ms pause before navigating, because the
  metadata write would otherwise be cancelled by the page unload.

### Runtime verification (this part worked)

Built a harness from `rhythm.html` with `supabase.js` stripped and `getSupabaseDb` stubbed to
a recorder, then called all three paths. Result — `markRhythmDone` fires on all of them with
the right payload, no errors:

```
{ "errors": [], "afterDirect": "{\"data\":{\"rhythm_done\":true}}",
  "applyPathCalled": true, "skipPathCalled": true, "navBlocked": 2 }
```

Trick worth remembering: `location.href` cannot be stubbed, so to observe a page that
navigates away, override `window.setTimeout` and swallow **only** the navigation timers
(500ms and 1200ms here), then assert you swallowed exactly two.

### Still not runtime-tested

`needsSetup = !gdata.rhythmDone` routing itself. Proving it needs the browser to land on
`index.html` vs `rhythm.html`, and Chrome hung every time — the destination page pulls
external CDNs that never settle, and `--host-resolver-rules=MAP * ~NOTFOUND` did not stop the
hang either. It is one boolean read by grep at a known line, but it is unproven end-to-end.
