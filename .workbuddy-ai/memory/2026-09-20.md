### 1. The `28:45` time bug (`js/shared.js`, `js/schedule.js`)
`toTimeStr()` has no wrap-around, so a task ending after midnight was saved as `"28:45"` — invalid for `<input type="time">`, which then blanks the field.

**The global fix is unsafe.** Three AI prompt strings (`shared.js` ~3839, ~6802, ~6842) deliberately use `toTimeStr((START_HOUR + VISIBLE_HOURS) * 60)` to describe the grid to the model as `"05:00 – 29:00"`. Adding `% 1440` there would silently change those prompts.

Instead added `toClockStr(minutes)` next to `toTimeStr` and converted **11 call sites** in `schedule.js` (card drag/resize writes, the drag tooltip). `toTimeStr` is untouched. Existing `"28:45"` values in storage are left alone deliberately — that needs a separate one-time cleanup.

Verified: 7 behaviour cases (1725→"04:45", 1740→"05:00", 1439→"23:59", negative input → "23:30").

### 2. Analytics that reported wrong numbers (`js/progress.js`)
- **`renderStreak`** was fed the period-filtered list, so any run crossing a week boundary read as broken; it also reset to 0 when today was still empty, and capped `bestStreak` at 7. Now reads the **full** `state.tasks` history, treats an empty today as "not broken yet", and computes the best run across all recorded dates.
- **Day-by-day table** summed durations over `!t.completed` only, so finishing work made the totals go **down**. Now sums every task in the day, and the Tasks column shows the true count.
- **`getFilteredTasks`** had no upper bound, so future-dated tasks inflated week/month totals. Added `endDate`.

### 3. Two-hour offset + silent storage failures
- **`js/schedule.js`** — work-hours mode renders the grid from 7am, but every position calculation assumed `START_HOUR` (5am), so cards, the now-line and drag maths sat two hours low. Added module-level `_gridStartHour` / `_gridEndHour`, set once in `renderGrid`, and converted **13 positioning sites** to use them. Left `START_HOUR * 60` alone in the `parseTime` helpers and the mobile day view — those are data-convention and internally consistent, not grid rendering.
- **`js/shared.js`** — the `localStorage.setItem` wrapper swallowed `QuotaExceededError`, so a full store lost data with no warning. It now **returns a boolean** (additive — callers that ignore it are unaffected) and shows a toast **once per session** via `_warnStorageFull()`. The warn flag is set before the toast call so a toast-triggered write cannot recurse.

### Reusable technique that worked well
Testing a browser script in Node: **extract the specific function by brace-matching the source and eval that in a `vm` context with stubs.** Loading a whole page script is fragile (progress.js needs dozens of shared.js globals), but extracting two functions tests the *real* code with almost no scaffolding. The naive alternative — copying the function into the test — tests a copy and proves nothing.

## Fixed the mislabelled analytics columns (Hans chose "Study + Daily")

The Analytics KPI cards and the day-by-day table had two columns labelled **"Deep Work"** and **"Study"** that counted the wrong things: `deepMins` summed `tag === 'daily'`, and `studyMins` summed **only** `tag === 'math'`. So "Study" ignored Physics, Bio, Chem, Eng and Mandarin — five of his six subjects — and "Deep Work" was really a Daily bucket.

Asked which way to fix it (this is a product decision, not a bug fix); Hans picked **Study + Daily**.

**Changes:**
- `js/progress.js` — added `const STUDY_TAGS = ['math','physics','bio','chem','eng','mandarin']` and `isStudyTag()` near the top so a new subject only needs adding in one place. `renderSummary` and the day-table loop now use `isStudyTag()`; `deepMins` renamed `dailyMins`.
- `progress.html` — KPI label and table header now read "Daily" and carry `data-i18n="an.daily"`.
- Element ids `statDeep` / `statDeepTrend` deliberately **not** renamed — they are internal hooks, and renaming risks missing a reference. A comment says what the id now means.

**Nice find:** `an.daily` already existed in the i18n dictionary with all three languages (Daily / Harian / 每日), so no dictionary work was needed. Because both elements now use `data-i18n`, the auto-translator skips them (it ignores elements with that attribute), so the now-dead `'Deep Work':'an.deep'` entry in `_ENG_TXT` was left alone rather than risking a wider change.

**Verified:** 8 tests against the real extracted `renderSummary` + `isStudyTag` — physics+mandarin now count as Study (was 0h), Daily only counts daily, all six subjects total correctly, no leakage between buckets, `isStudyTag` rejects `daily` and unknown tags, and the trend hook receives the study total.
